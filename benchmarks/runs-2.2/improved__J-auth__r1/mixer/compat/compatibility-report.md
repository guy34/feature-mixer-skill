## database:primary-key:user

- **Conflict:** User primary keys differ (A: integer, B: text)
- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** critical
- **Possible solutions:** Pick one key type for the merged entity and re-key the other source's rows; Keep a legacy_id column holding the old key during migration
- **Recommended resolution:** Use one key type (uuid is usual for merged data) and add a legacy_id column while migrating
- **User approval required:** yes
- **Status:** resolved (One User entity keyed by an opaque random text id (uuid4 hex) generated by the unified app; A's integer ids and B's 'lu-<n>' ids are not reused (no persisted source data exists; a legacy_id would hold them if data were ever imported).)

## application:auth-provider:provider

- **Conflict:** Identity providers differ (A: own (local accounts); B: external oauth provider (google-style); C: none (authorization only))
- **Affected applications:** A, B, C
- **Affected features:** not linked to a feature
- **Severity:** high
- **Possible solutions:** Choose one identity provider and migrate accounts to it; Link accounts by verified email during migration
- **Recommended resolution:** One identity system for the unified app
- **User approval required:** yes
- **Status:** resolved (One identity system (the unified identity module) with two sign-in methods: local password and a federated OAuth provider behind an adapter; the provider callback data (provider, subject, email, email_verified) is the input to login_oauth. Real provider token verification is not testable here.)

## application:authorization-model:model

- **Conflict:** Authorization models differ (A: single role; B: single role; C: role-based access control)
- **Affected applications:** A, B, C
- **Affected features:** not linked to a feature
- **Severity:** high
- **Possible solutions:** Choose one authorization model and express the others' rules in it
- **Recommended resolution:** One authorization model with one permission check function
- **User approval required:** yes
- **Status:** resolved (One role-based model (C's): roles viewer/editor/admin as permission sets and one can(role, permission) check used by every privileged action.)

## application:identity-linking:accounts

- **Conflict:** password sign-in (A) and federated sign-in (B) will meet in one account table: the same person can arrive twice, or an attacker can claim an account through an unverified email
- **Affected applications:** A, B
- **Affected features:** not linked to a feature
- **Severity:** high
- **Possible solutions:** Link a social or SSO login to an existing account only through a verified email; Keep separate accounts and offer a manual, authenticated link step
- **Recommended resolution:** Never merge accounts on an unverified email: that is an account-takeover path
- **User approval required:** yes
- **Status:** resolved (User decision: one account per person; a federated sign-in joins an existing account only when the provider says email_verified is exactly True and the email is owned by an existing account; otherwise it is a separate account. Never link on an unverified email.)

## application:permission:role-change-rules

- **Conflict:** C's set_role trusts a role string from the caller and accepts any new role name; the user requires that only an admin changes roles and nobody raises their own role
- **Affected applications:** C
- **Affected features:** M05
- **Severity:** high
- **Possible solutions:** Resolve the caller from the session; admin only; validate the role; refuse raising one's own role; Keep C's behaviour
- **Recommended resolution:** Caller from session token; PermissionError unless admin; unknown role rejected; self-raise refused
- **User approval required:** yes
- **Status:** resolved (set_role(token, user_id, role): caller resolved from the session; PermissionError unless the caller is admin (invalid session included); role must be a known unified role (ValueError); target must exist (KeyError); nobody may raise their own role (PermissionError) (user decision).)

## application:roles:roles

- **Conflict:** Role sets differ (A: user; B: member; C: admin, editor, viewer)
- **Affected applications:** A, B, C
- **Affected features:** not linked to a feature
- **Severity:** high
- **Possible solutions:** Map every source role to a unified role set and write the mapping down; Model special powers (such as approving) as permissions, not extra roles
- **Recommended resolution:** One role set plus explicit permissions; map every source role
- **User approval required:** yes
- **Status:** resolved (One role set (viewer, editor, admin) with role_mapping A:user->editor, B:member->viewer, C:viewer/editor/admin unchanged (user decision). Special powers stay permissions (manage_roles).)

## application:session:session

- **Conflict:** Session mechanisms differ (A: opaque bearer token in an in-memory store, no expiry; B: none in the source (callback returns the account record); C: none)
- **Affected applications:** A, B, C
- **Affected features:** not linked to a feature
- **Severity:** high
- **Possible solutions:** Choose one session mechanism (http-only cookie sessions are the safer default for web apps); Use tokens only where a client cannot hold cookies
- **Recommended resolution:** One session mechanism for the whole app
- **User approval required:** yes
- **Status:** resolved (One session mechanism: an opaque random token (secrets.token_urlsafe(32)) stored only as its SHA-256, with an expiry (default 8 h, configurable), revocable by logout; both sign-in methods issue it. A web layer would carry it in an http-only secure cookie.)

## application:workflow:duplicate-registration

- **Conflict:** A overwrites an existing account when the same email registers again; with one account per person this would let anyone take over an account (including one created or linked by OAuth)
- **Affected applications:** A, B
- **Affected features:** M01, M03
- **Severity:** high
- **Possible solutions:** Refuse registration when the normalised email already belongs to a user; Keep A's overwrite behaviour
- **Recommended resolution:** Refuse a duplicate registration with AuthError; never overwrite
- **User approval required:** yes
- **Status:** resolved (Refuse registration when the normalised email is already owned by an account (password or verified federated); raise AuthError and never overwrite.)

## database:enum:user.role

- **Conflict:** User.role allows different values (A only: user; B only: member; 2 values in all)
- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** high
- **Possible solutions:** Define one value set and a mapping from every source value to it; Keep the field per source if the states really differ
- **Recommended resolution:** One value set with an explicit mapping; values without a mapping block the migration
- **User approval required:** yes
- **Status:** resolved (One value set: viewer, editor, admin. Mapping A user->editor, B member->viewer, C roles unchanged (user decision in task.md); unknown source roles raise KeyError.)

## database:field-meaning:user.email

- **Conflict:** User.email (A:email, B:email) means different things (A: 'lowercased; the dict key'; B: 'as sent by the provider, not normalised, not unique')
- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** high
- **Possible solutions:** Keep two fields with distinct names (for example owner_id and created_by); Merge them only if the user confirms they mean the same
- **Recommended resolution:** Ask the user; never merge fields because their names match or an alias says so
- **User approval required:** yes
- **Status:** resolved (User.email is the person's normalised (trimmed, lowercased) email. A's lowercased key and B's provider email are kept apart from ownership: a PasswordCredential owns its email (unique), a federated Identity records the provider's email and whether it was verified; only owned emails are used for linking.)

## database:field-meaning:user.id

- **Affected applications:** A, B

- **Severity:** high
- **Possible solutions:** Keep two fields with distinct names (for example owner_id and created_by); Merge them only if the user confirms they mean the same
- **Recommended resolution:** Ask the user; never merge fields because their names match or an alias says so
- **User approval required:** yes
- **Status:** resolved (Neither source id survives: A's counter and B's 'lu-' counter are both replaced by one generated opaque id; the meaning is 'the unified user's id'.)

## database:deletion-semantics:user

- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** medium
- **Possible solutions:** Choose soft or hard delete for the merged entity and convert the other source's rows; Keep deleted rows from the soft-delete source as archived

## database:duplicate-entity:user

- **Conflict:** User exists in A:User, B:Account; fields not shared: hash (only A), provider (only B), salt (only A), subject (only B)
- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** medium
- **Possible solutions:** Merge into one table holding the fields kept features need; Keep separate tables if the two only share a name, and rename one
- **Recommended resolution:** Merge only once it is confirmed they mean the same thing; then list every field's origin in architecture.json
- **User approval required:** no
- **Status:** resolved (Merge A:User and B:Account into one User (alias recorded with reason); sign-in methods become child records: PasswordCredential (A's email, salt, hash) and Identity (B's provider, subject, email, email_verified).)

## database:nullability:user.email

- **Conflict:** User.email is A: required, B: optional
- **Affected applications:** A, B
- **Affected features:** M01, M02, M03
- **Severity:** medium
- **Possible solutions:** Keep the field nullable; Make it required with a default for rows that have no value
- **Recommended resolution:** Do not make a field required until every source row has a value or a default is agreed
- **User approval required:** no
- **Status:** resolved (User.email optional (a provider may send none); password users always have one; a federated sign-in without an email never links.)
